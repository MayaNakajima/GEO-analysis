# GEO 定点観測 分析アプリ｜引き継ぎプロンプト（v1）
## 株式会社オンワードコーポレートデザイン ／ 生成AI出現モニタリング

用途：別チャット（別担当者・別セッション）で本アプリの開発・改修を継続するための引き継ぎ資料。
下部の「新チャットでの最初のひとこと（コピペ用）」をそのまま貼れば、文脈を引き継いで作業を再開できる。

---

## 1. これは何か

`monitoring`（定点観測アプリ）が出力する回答全文つき row データ（`results_*.csv`）を分析し、
**「なぜ当社が出ないか・何を直すか」** を掘り下げる **自己完結型 HTML ダッシュボード** を生成するアプリ（`GEO-analysis`）。
生成物 `analysis.html` はブラウザ単体で開ける（外部依存は CDN の Chart.js のみ）。

---

## 2. 現在の到達点（完成しているもの）

- `generate.py`（Python 標準ライブラリのみ）：CSV＋reference を読み、集計・競合抽出し、単一 HTML に JSON 埋め込みで出力。
- 実装済み分析：
  - **P1 競合共起**（未言及回答から競合を抽出・ランキング・ドメイン別・回答全文ドリルダウン）
  - **P1 多軸クロス集計**（行/列軸選択・セルクリックでドリルダウン・Set2 の崖を自動言語化。軸に回(run)/タイミングも選べる）
  - **回(run)/タイミング(timing)粒度**（ファイル名から解析。同日複数回を分離。全回まとめ／回ごとを切替）
  - **過去回比較**（A/B の 2 回を選び、出現率デルタ・競合の増減・質問の反転(hit↔miss)・回答差分ドリルダウン。r1↔r2 でブレ確認も可）
  - **P2 引用URL分析**（`urls_found` 集計。非グラウンディングの現状は空状態表示）
  - **P2 自社突合**（`reference.md` の掲載実績 × AI 言及有無＝「掲載あるが未言及」を可視化）
- **P3 競合サイト突合は未実装（設計のみ）**。
- git 初期化・初回コミット済み（main）。`analysis.html` は `.gitignore` 対象（再生成可能）。

---

## 3. 前提（重要・測定対象）

- 稼働モデルは **Claude 単体＝非グラウンディング**。測っているのは「AI の学習記憶に当社があるか」。
- 検索引用（`urls_found`）は Perplexity 等のキー許可後に測定（将来）。現状は空。
- 実測では出現はほぼ **指名（D1）に限定**、業種・実績（D2）以下は 0%＝ **崖は D1→D2**。
- 本アプリの目的は「崖より下でなぜ消えるか」を回答本文から掘ること。

---

## 4. データ構造（generate.py が読む前提）

- 入力：`monitoring/data/results/results_*.csv`（UTF-8 BOM、複数ファイル）。
  主な列：run_date, run_timestamp, question_id, axis_domain, domain_label, axis_type, type_label,
  axis_stakeholder, stakeholder_label, abm_relevant, model_id, model_name, question,
  **answer（回答全文）**, mention_detected, mention_position, entities_found, **urls_found**,
  context_snippet, question_set（set1/set2）, specificity_tier（D1〜D4／set1は空）。
- **スキーマ差異**：初期 CSV（Set1のみ）は `question_set`/`specificity_tier` が無い → `generate.py` が既定値で吸収。
- 自社実績：`Set2_実績スクレイピング_reference.md`（業種別 掲載顧客・事例・URL）。
- パスは `config.json` に定義（monitoring は別環境・今後修正あり得るため、場所が変わったら config を直す）。

---

## 5. 改修時の勘所

- **競合抽出**は `generate.py` の `extract_competitors()` / `_is_company_like()` / `_norm_key()` に集約。
  精度改善はここ。除外語は `GENERIC_STOP`、自社は `OWN_NAMES`、顧客ヒントは `CUSTOMER_HINTS`＋reference 由来。
- **集計・UI** は HTML テンプレート内の JavaScript（`renderComp` / `renderCross` / `renderUrl` / `renderSelf`）。
  重い抽出は Python 側で行単位に 1 回、フィルタ・集計は JS 側で動的、という分担を崩さない。
- **埋め込み安全性**：`render_html()` で `<`,`>`,U+2028/2029 をエスケープ済み。テンプレ改修時も維持すること。
- monitoring とは疎結合（同じ CSV を読むだけ）。monitoring の改修に追随不要、スキーマ変更時のみ吸収ロジックを更新。

## 6. 作業フロー（ローカルgit：ブランチ運用）

改修は **必ずブランチを切って作業 → 確認OK → main にマージコミット** の順で行う。
`main` には常に「動作確認済み」の状態だけを置く。実行は Anaconda Prompt。

### 手順

**① 最新の main から作業ブランチを切る**
```bat
cd /d C:\Users\612316\Documents\GitHub\GEO-analysis
git checkout main
git status                        REM 変更が残っていないこと（クリーン）を確認
git checkout -b feature/○○○      REM 作業ブランチを作成して移動
```
ブランチ名の例：`feature/competitor-dict`（競合辞書強化）、`fix/crosstab-run-axis`（不具合修正）、`docs/handoff-update`（文書更新）。

**② 作業する（コードや文書を編集）**

**③ 動作を確認する（コミット前に必ず）**
```bat
python generate.py                REM analysis.html を再生成
```
→ 生成された `analysis.html` をブラウザで開き、変更点が意図通りか、他タブが壊れていないかを目視確認。
（`analysis.html` は `.gitignore` 対象なのでコミットには含まれない。確認用に手元で生成する。）

**④ 作業ログを残す（`docs/worklog.md` に追記）**
ブランチ単位で、目的・作業内容・確認結果を `docs/worklog.md` の一番上に追記する（書式は §6-2）。

**⑤ ブランチにコミットする（件名＋本文で作業内容をコメント）**
コミットメッセージは **「件名（1行）＋空行＋本文（詳細）」** で書く。Anaconda Prompt ではエディタを開かず、
`-m` を複数指定すると各段落になる（1つ目＝件名、2つ目以降＝本文）。
```bat
git add -A
git commit -m "feat: 競合辞書に医療系を追加" -m "・ナガイレーベン等の表記ゆれを正規化" -m "・除外語に一般語3件を追加。07-28データで再生成し件数が妥当なことを確認"
```
作業が複数段階なら ③〜⑤ を繰り返す（小さくコミット）。本文には「なぜ・何を・どう確認したか」を残す。

**⑥ 確認OKになったら main にマージコミットする**
```bat
git checkout main
git merge --no-ff feature/○○○ -m "Merge feature/○○○: 変更内容の要約"
```
`--no-ff` を付けると、必ず **マージコミット** が作られ、履歴に「この機能単位でまとめて入った」ことが残る。

**⑦ 作業ブランチを片付ける**
```bat
git branch -d feature/○○○         REM マージ済みブランチを削除
git log --oneline --graph -n 10    REM 履歴（枝分かれとマージ）を確認
```

### ルール・注意
- `main` に直接コミットしない。必ずブランチ経由。
- **作業内容のコメントは 2 か所に残す**：(1) コミット本文（件名＋空行＋本文、`-m` を複数指定）、(2) `docs/worklog.md`（ブランチ単位の記録）。
- コミットメッセージの種別プレフィックス：`feat`（機能追加）／`fix`（修正）／`docs`（文書）／`refactor`（整理）。
- マージ前に必ず ③ の再生成＋ブラウザ確認を行い、OKになってから ⑥ を実行する。
- コンフリクトが出たら、該当ファイルを修正 → `git add` → `git commit` でマージを完了させる。
- リモート（GitHub 等）を使う場合は、⑥の後に `git push origin main`、作業中は `git push origin feature/○○○`。ローカル運用のみなら push は不要。
- 各コミットの本文は `git show <ハッシュ>`、`git log`（本文込み）で後から読める。ブランチ削除後もコミット本文と worklog は残る。

### コマンド早見表
| やりたいこと | コマンド |
|---|---|
| 作業ブランチ作成 | `git checkout -b feature/○○○` |
| 作業ログ追記 | `docs/worklog.md` の先頭に §6-2 の書式で記入 |
| 変更をコミット（本文付き） | `git add -A` → `git commit -m "feat: 件名" -m "本文1" -m "本文2"` |
| 生成物で確認 | `python generate.py` → `analysis.html` を開く |
| main へマージ（マージコミット） | `git checkout main` → `git merge --no-ff feature/○○○ -m "Merge ..."` |
| ブランチ削除 | `git branch -d feature/○○○` |
| 履歴・本文確認 | `git log --oneline --graph` ／ `git show <ハッシュ>` |

## 6-2. 作業ログ（docs/worklog.md）の書式

ブランチ単位で `docs/worklog.md` の **一番上（新しい順）** に追記する。書式は以下（コピーして使う）：

```markdown
## YYYY-MM-DD  branch: feature/○○○
- 目的：（何のための作業か）
- 作業内容：
  - （変更点1）
  - （変更点2）
- 確認：python generate.py 再生成＋ブラウザ確認（結果・所見）
- コミット：<短縮ハッシュ>／マージ：<マージコミット短縮ハッシュ>
```

コミット本文が「各コミットの詳細」なのに対し、worklog は「ブランチ＝作業単位のまとめ」。両方あることで、履歴を追わなくても作業の流れを把握できる。
