# GEO 定点観測 分析アプリ｜仕様書（v1）
## 株式会社オンワードコーポレートデザイン ／ 生成AI出現モニタリング

作成日：2026-07-28 ／ 対象：`GEO-analysis`（分析アプリ）
位置づけ：改善案 `ダッシュボード改善案_20260728.md` §3「rowデータ×スクレイピング分析アプリ」の実装仕様。

---

## 1. 目的

定点観測アプリ（`monitoring`）が出力する **回答全文つき row データ（`results_*.csv`）** を読み込み、
**「なぜ当社が出ないのか・何を直すか」** を掘り下げるための自己完結型 HTML ダッシュボードを生成する。

内蔵ダッシュボードが「今どうなっているか（出現率・推移・崖・ブレ）」を担うのに対し、
本アプリは **回答本文の内容分析・突合（競合共起／引用URL／自社実績）** に特化する。

---

## 2. 役割分担（内蔵ダッシュボード vs 本アプリ）

|  | 内蔵ダッシュボード（`monitoring/src/dashboard.py`） | 本アプリ（`GEO-analysis`） |
|---|---|---|
| 目的 | 日々の定点監視・軽量 | 回答全文の深掘り・突合分析 |
| 入力 | `data/reports/*.json`（集計済み） | `data/results/results_*.csv`（回答全文・生データ） |
| 見るもの | 出現率・推移・特異度カーブ・ブレ | 回答本文／競合共起／引用URL／自社突合 |
| 更新頻度 | 実行のたび自動生成 | 分析したいときに随時（`generate.py` 実行） |
| ネット接続 | 不要 | 不要（P3 のみ将来スクレイピング） |
| 一言 | 「今どうなっているか」 | 「なぜそうなのか・何を直すか」 |

**導線**：内蔵側で「崖は D2」と分かる → 本アプリで「D2 で誰に負けているか・自社実績ページはあるか」を掘る。

**2026-09-29 更新（関係者向け画面の一本化）**：関係者が見る画面は **`analysis.html` だけ** とする。冒頭の「ホーム」タブ（§5-0）で
「今どうなっているか → なぜか → 次に何をするか → 何を議論するか」を 1 画面にまとめ、monitoring の `index.json`・`insights_*.json` を読むだけで取り込む。
内蔵 `dashboard.html` / `insights.html`（Box「GEO」）は **運用者向け**（計測の監視・不具合確認）と位置づける。monitoring 側は変更しない。

## 3. 前提（測定対象の理解）

- 稼働モデルは **Claude 単体＝非グラウンディング**。測定対象は「AI の学習記憶に当社があるか」。
- 検索引用（`urls_found`）の測定は Perplexity 等の検索引用型モデルのキー許可後（将来）。
- 現状の実測では出現はほぼ **指名質問（D1）に限定**、業種・実績質問（D2）以下は 0%＝ **崖は D1→D2**。
- 本アプリはこの「崖より下でなぜ消えるか」を、回答本文から掘り下げるのが役割。

## 4. 入力データ

### 4-1. results_*.csv（UTF-8 BOM・複数ファイル）
`monitoring/data/results/` 配下。主な列：

| 列 | 用途 |
|---|---|
| run_date / run_timestamp | 実行日・時刻（期間フィルタ・時系列） |
| question_id | 質問ID（ドリルダウンのキー） |
| axis_domain / domain_label | 事業ドメイン（C1〜C7, C3-EC） |
| axis_type / type_label | 質問タイプ |
| axis_stakeholder / stakeholder_label | 想定ステークホルダー |
| model_id / model_name | 稼働モデル |
| question | 質問文 |
| **answer** | **回答全文（本アプリの主対象）** |
| mention_detected | 当社言及の有無（True/False） |
| mention_position / entities_found | 言及位置・検出エンティティ |
| **urls_found** | **引用URL（P2で集計・現状は空）** |
| context_snippet | 言及周辺の抜粋 |
| question_set | set1 / set2 |
| specificity_tier | D1〜D4（set1 は空欄） |

**スキーマ差異への対応**：初期（2026-07-16）の Set1 のみの CSV には `question_set` / `specificity_tier` 列が無い。
`generate.py` は欠損時に `question_set="set1"`・`specificity_tier=""` として吸収する。

### 4-2. Set2_実績スクレイピング_reference.md
自社サイトの掲載顧客・事例・URL を業種（C1〜C5）別にまとめた一次資料。P2 自社突合の初期データ。

### 4-3. データの受け渡し形式（monitoring → 本アプリ：reports_dir）
`config.json` の `reports_dir`（既定 `monitoring/data/reports`、`--reports-dir` で上書き）から、ホームタブ用に次を **読むだけ**。
どれが欠けても・壊れていても生成は失敗させず、ログに `[WARN]` を出して、ホームの該当ブロックを「データなし」と表示する。

**(1) `index.json`**：配列。1要素＝1タイミング。

| キー | 型 | 用途 | 欠けていた場合 |
|---|---|---|---|
| `timing_id` | 文字列 `YYYYMMDD_HHMMSS` | 最新回（results CSV の timing）との突き合わせ | その回の参考値を「データなし」 |
| `timing_label` | 文字列 | （表示補助） | 無視 |
| `overall_mean` | 数値（%） | 「計測上の注意」の参考値（monitoring 側の集計＝全行が分母） | 参考値を「データなし」 |
| `overall_sd` | 数値 | （現状未表示） | 無視 |
| `stability` | 数値（%） | 参考値として併記 | 「–」 |
| `models` | 文字列の配列 | 稼働モデル一覧・非グラウンディング判定 | 最新回 CSV の `model_name` で代替 |

ファイル自体が無い／配列でない／JSON として壊れている → `index` を空として扱う。

**(2) `insights_*.json`**：ファイル名は `insights_YYYYMMDD_HHMMSS.json` と `insights_YYYYMMDD_HHMMSS_rN.json` の2種類が混在するため両方に対応し、
**日時部分でソートして最新を採用**（最新が壊れていれば 1 つ前を採用し `[WARN]`）。採用ファイル名は生成ログに出す。
採用した日時が最新の results CSV の timing と一致しない場合、ホームに「示唆は ◯/◯ 実行分に基づく」と注記する。

| キー | 型 | 用途 | 欠けていた場合 |
|---|---|---|---|
| `summary` | オブジェクト `{total, detected, overall_rate, nd_count}` | （埋め込みのみ・表示は CSV から計算） | 影響なし |
| `weak_cells` | 配列 `{domain, type, total, detected, rate, miss, fail_models, sample_questions}` | （埋め込みのみ・将来用） | 影響なし |
| `extraction.nd_count` | 数値 | Q2 の母数（非出現回答数） | 「–」 |
| `extraction.competitors` | `[名前, 件数]` の配列 | Q2「代わりに挙がった競合」上位5 | Q2 の表を「データなし」 |
| `extraction.attributes` | `[観点, 件数]` の配列 | Q2「重視された観点」上位5 | 同上 |
| `actions` | 配列 | 3)次にやること・Q3 の上位3件（`priority` 高→中→低、同順位は元の順） | 3) と Q3 を「データなし」 |
| `actions[].domain` / `.type` | 文字列（domain_label / type_label） | 対象の表示・担当事業の引き当て（`domain_owner`） | 空表示／担当「未割当」 |
| `actions[].priority` | 文字列（高/中/低） | 並び順・バッジ | 「–」・末尾扱い |
| `actions[].rate` / `.miss` / `.total` | 数値 | 出現率・非出現件数 | 空表示 |
| `actions[].playbook` | 文字列 | 打ち手・Q3「何を直すか」 | 「–」 |
| `actions[].cover_attributes` | 文字列の配列 | 重視されている観点 | 「–」 |
| `actions[].beating_competitors` | 文字列の配列 | 想起されている競合 | 「–」 |

insights が 1 つも無い／すべて壊れている／`reports_dir` が存在しない → 3)・Q2・Q3 を「データなし」。1)・2)・Q1 は CSV から計算するため表示される。

**(2-2) `judge_*.json`**（monitoring の `src/answer_judge.py`＝回答の読み取り判定が出力）：`judge_YYYYMMDD_HHMMSS(_rN).json` の**最新**を採用
（壊れていれば 1 つ前。採用ファイル名は生成ログに `judge:` として出す）。「推薦の読み取り」タブとホーム Q2 の1行に使う。
`google`（Google 検索チェックとの突き合わせ）は Google参考値タブと重なるため読まない。`suggestions` のうち `kind: "google"` のものも表示しない。

| キー | 型 | 用途 | 欠けていた場合 |
|---|---|---|---|
| `summary` | オブジェクト（`answers, judged, rec, pick, kinds, own_status_total` など） | タブ冒頭の要約・KPI | タブ全体を「データなし」 |
| `stakeholders` | 配列 `{stakeholder, rec_total, counts{状態: 件数}, absent_rate, non_rec}` | ① 立場別の自社の扱い | ① を「データなし」 |
| `reasons` | `{columns:[{name, listed}], rows:[{reason, values[]}]}`（列0が自社） | ② 推される理由・ホーム Q2 の「語られていない理由」（競合平均−自社 ≥ 20pt） | ② を「データなし」・Q2 の行なし |
| `suggestions` | 配列 `{title, text, kind?}` | ③ 示唆 | 「示唆はありません」 |
| `survival` | 配列 `{name, listed, kept, rate, is_own}` | ④ 最後のおすすめまで残った割合（10回未満は「（少）」） | ④ を「データなし」 |
| `runs` / `model` / `generated_at` / `own_label` | 文字列 | 対象期間・判定AI・作成日時の表示、自社列の判定 | 「–」 |

judge が無い（monitoring で判定を一度も実行していない）→ 「推薦の読み取り」タブを「データなし」。他のタブには影響しない。

**(3) config 側の補助設定**：`measurement_notes`（`[{date:"YYYY-MM-DD", label, note}]`＝計測の断絶）、`domain_owner`（domain_label → 担当事業）、
`grounding_model_keywords`（モデル名にこれを含めば Web 検索ありとみなす）。

## 5. 分析機能（改善案 §3-2 の優先度順）

### 5-0. ホーム（関係者向けの入口・初期表示）【実装済み】
TABS の先頭。上から次の順に表示する。
1. **今回の結論**：最新回（有効行のある最後のタイミング。同一タイミングの r1/r2 はまとめる。1タイミング1回なら全回サマリーの run 表示と同値）の出現率（分母＝有効行＝エラー・空回答を除く。全回サマリーと同じ `runRate`）と前回（有効行のある 1 つ前のタイミング）比。
   ▲改善／▼低下／±横ばい（0.1pt 単位で判定）を色と言葉で併記。前回と最新回の間に `measurement_notes.date` があれば「比較対象外」。
   **指名**＝Set2 の D1 ＋ Set1 のうち質問文に社名（`OWN_NAMES`）を含むもの、**非指名**＝それ以外（Set2 D2〜D4・Set1 一般）で出現率を分けて表示し、
   非指名が 5% 未満かつ指名より低ければ「非指名での出現が課題」と自動で結ぶ。
   その下に **質問セット別**（Set1＝一般質問／Set2＝特異度つき D1〜D4）の出現率・ヒット/有効行・前回比と、
   **Set2 特異度カーブ**（D1→D4 の出現率。D1 以外で最初に 10% 未満になる所を「崖」と表示＝クロス集計の崖の自動説明と同じ基準、ただし分母は有効行）を1行で添える。
2. **計測上の注意**（折りたたみ・初期は開）：断絶、最新回の全行／有効行／エラー／空回答、index.json の参考値（全行分母のため差が出る旨）、
   稼働モデル一覧。全モデルが非グラウンディングなら「学習データ上の認知を測定中。サイト施策の効果は週単位では動きにくい」と明記。
3. **次にやること**：insights `actions` 上位3件（優先度・事業ドメイン×質問タイプ・担当事業・playbook・cover_attributes・beating_competitors）。
4. **今回の議論ポイント**：Q1 前回→最新回の反転（過去回比較の `byQid` を再利用。行クリックで A/B 回答比較）、
   Q2 `extraction.competitors` / `attributes` 上位5件、Q3 上位3件を担当者・期限・メモ欄が空欄の表で（印刷して会議で記入）。
5. **詳しく見るには**：各既存タブへのリンクと一言説明。

用語（出現率・有効行・指名/非指名・非グラウンディング）は見出し横の「?」でツールチップ説明。
印刷は `@media print`（A4横）で表示中のタブのみを出し、ホームは 2 枚に収まる（2026-09-28 データで確認）。
全回サマリーの推移チャートには `measurement_notes` の位置に破線と、それより前の背景塗り分けを付ける（annotation プラグインは使わずインラインの Chart.js プラグインで描画）。


### P1｜競合共起分析【実装済み】
`mention_detected=False` の回答本文から、代わりに挙がる **競合企業名を抽出・ランキング**。
ドメイン別に「どの土俵で誰に負けているか」を集計。行クリックで根拠の回答全文へドリルダウン。

### P1｜多軸クロス集計 ＋ ドリルダウン【実装済み】
行軸・列軸を **回(run)／タイミング**／ドメイン／特異度ティア／質問タイプ／ステークホルダー／モデル／実行日／質問セット から選択し、
出現率クロス表を生成。セルクリックで該当質問・回答全文の一覧を展開。
Set2 の特異度カーブから **崖の位置（例 D1→D2）を自動で言語化**。
軸に「回(run)」を置けば全回の出現率が横並びになり、回ごとの推移を1表で見られる。

### 回（run）・タイミング（timing）の粒度【実装済み】
定点観測は同じ日に複数回実行され得る（例：同一日に r1/r2）。本アプリは実行日だけでなく **回単位** で分析できる。
- **run**：`results_*.csv` ファイル 1 つ＝ 1 回（r1/r2 を個別に扱う）。
- **timing**：同一タイミング（例 `170500`）の r1/r2 をまとめた単位（＝ブレを均した 1 回分）。

全タブ共通フィルタに「タイミング」「回(run)」を追加。既定は全回まとめ（フィルタ未選択）。

### 過去回比較【実装済み】
2 つの回（A=過去／B=比較）を選び、粒度（run／timing）を切り替えて A→B の変化を見る専用タブ。
- **全体・ドメイン別・特異度別の出現率デルタ**（改善↑＝緑／低下↓＝赤）。
- **競合の増減**：登場回答数を A/B で比較し、新規登場・消失・増減を表示（増＝負けの拡大、減＝改善の可能性）。
- **質問の反転**：共通質問を hit↔miss で分類（出た↑／消えた↓／出続け／消え続け）。
- **回答差分ドリルダウン**：反転質問クリックで A と B の回答全文を並べて比較。
- 同一タイミングの r1↔r2 を A/B に選べば、**ブレ（同条件を複数回実行したときのばらつき）** の確認にも使える。

### 全回サマリー｜過去回すべての比較・総合【実装済み】
過去すべての回を1画面で。**出現率の推移チャート**（run／timing 切替）＋**回ごとテーブル**（有効行・hits・出現率・エラー行数・空・ユニーク競合・トップ競合）＋**総合集計**（全回プールのドメイン別・特異度別 出現率＋回ごとの**ブレ**＝最小〜最大の幅）。
出現率は**有効行（`atype` がエラー・空でない行）**を分母に算出し、全行エラーの回は「–」として集計から自動除外する（APIキー未設定などのデータ欠測がプール値・推移・ブレを歪めないため）。回クリックでその回のヒット回答へドリルダウン。

### Google参考値｜GSC（Google 自然検索）との並列比較【実装済み・フェーズ1】
設計：GEO リポジトリ `Google参考値観測_設計_v1.md`。Claude と**同じ設問**について、Google 自然検索での自社サイトの順位（GSC）を**参考値**として並べる。
- **入力**：`gsc_dir` の GSC 手動ダウンロード（`<サイト略称>｜GSC｜Performance-on-Search*.xlsx`。略称 CO／UN／SCH／MED／MED-EC／IS）と、
  設問マスタ `google_keywords_csv`（monitoring/config/google_keywords.csv：設問ID・観測キーワード・意図のズレ・GSC参照クエリ・参照クエリとの差）。
  xlsx は `gsc_reader.py` が標準ライブラリ（zip＋XML）で読む。期間は「フィルタ」シートの日付で判定し、1日〜月末ちょうど＝**月次**、それ以外＝**期間集計（参考）**。
  同じサイト・種類・期間のファイルが複数あれば更新日時が新しいものを採用。
- **やること（判定）**：Claude で出現（出現率 > 0%。有効行で集計）→「維持」／Claude 0% かつ GSC参照クエリの平均順位 10位以内 →「**AI向けに直す**」／
  11〜20位 →「あと一歩」／21位以下 →「順位を上げる」／GSC にデータなし →「検索チェック待ち」。担当は `domain_owner`（ホームと同じ）。
- **①次にやること**：「AI向けに直す」「あと一歩」「検索チェック待ち」の3枚のカード。優先度・理由・やることのチェックリスト・
  効果の大きい設問（同じ GSC参照クエリはまとめ、表示回数の多い順に上位3件。「AI向けに直す」は Claude が代わりに挙げた会社も）・「一覧で見る」ボタン。
- **②担当別**：担当 × やることの件数表。数字クリックで③を絞り込む。
- **④判定の根拠**：縦＝Claude 出現／なし、横＝Google 10位以内／11位以下／データなし のマス目（クリックで③を絞り込み）。
- **期間**：既定は「最新」＝サイトごとに最新のファイル（月次があれば最新の月次）。Claude 側は、Google 側が月次ならその月、月次でなければ全期間。
- **③設問一覧**：やること・担当・Claude 出現率・**次の一手**（やることと順位から作る1文）・**Claude が代わりに挙げた会社**（期間内の未言及回答から抽出した候補の上位3件。
  課題解決型 A2 と自社について聞く設問 A6・D1 は、太字が施策名になる／競合比較の対象でないため表示しない）・観測キーワード（⚠＝意図のズレあり）・
  GSC参照クエリ（≈＝観測KWより広い）・Google 順位（代表サイト＝表示回数が最大）・表示回数。並びはやることの優先度 → 表示回数の多い順。
  行クリックで期間×サイトの値、月別推移（月次 GSC が1か月以上＋2か月以上の表示で折れ線）、施策の記録（config `action_notes`）を表示。
- **3つの出現率・外部での言及【実装済み】**：タブ冒頭に Claude の出現率・Google の AI による概要での自社引用率・Google 上位10件率（検索チェック）を並べ、事業領域別の表も出す。
  やることに「外部での言及を増やす」（Claude 0% かつ検索チェックで AI による概要に自社が引用済み。順位に関係なくこちらを優先）を追加し、「AI向けに直す」は「AI向けにページを直す」（概要にも未引用・10位以内）に名称変更。次の一手に自社ページの URL（検索チェックで取れた場合）。「外部での言及を増やす」カードに、概要がよく引用する自社以外のサイト（YouTube・PR TIMES 等）を表示。
- **判定・表示の調整（全269件の結果から）【実装済み】**：
  - 判定（自動）＝検索チェックのキーワード・設問文のうち順位の高い方。どちらも上位10件に自社がなく、GSC の平均順位が11〜20位なら「あと一歩」。
  - 競合は記録時の判定ではなく、上位10件のドメインと今の辞書（monitoring/config/google_competitor_domains.json：competitors・media）で判定し直す。
  - AI による概要の引用元を 自社／グループ／競合／媒体／その他 に分類。「外部での言及を増やす」カードには媒体（情報を載せる先）だけを出し、競合は参考として別に表示。
  - グループサイト（config `group_domains`、既定 onward-hd.co.jp）は自社の率に含めず、上位10件・概要の引用元の件数を別枠で表示。
  - 「外部での言及を増やす」は Google 10位以内（優先）と10位外に分け、一覧も同じやることの中で10位以内を先に並べる。
  - Claude の集計期間：GSC が月次ならその月、そうでなければ検索チェックと同じ月（例 2026-09）。この期間に有効な回答がない設問は「Claude 未計測」で判定から外す。
  - **分析の基準**（タブ上部の「📘 この分析の基準」）：データの出どころと状態（範囲・件数・最終更新）、3つの率の計算と読み方、やることの判定ルール（順番つき）、用語、注意点。
    ①の各率・表の見出しに「?」の説明。ホームの1行から「分析の基準」を開ける。①の事業領域別の表に「上位10件によく出る競合」。
- **施策管理表【実装済み】**：Box の `GEO-analysis\Google参考値_施策管理.xlsx`（config `action_xlsx`。空なら share_dirs の最初のフォルダ）を
  `gsc_reader.load_actions()` が読む。列＝設問ID・担当（事業）・担当者・状態（未着手／対応中／完了／見送り）・期限・実施日・実施内容・対象ページURL・メモ。
  1設問に複数行＝履歴（下の行が最新）。「担当（事業）」はその設問の担当を上書き（空なら domain_owner）。
  一覧に「施策」列（状態・担当者）、フィルタ「施策の状態」、次の一手は状態を反映（対応中／完了→推移で効果確認／見送り）。
  「次にやること」カードと担当別の件数は、完了・見送りを除いた設問で数える。設問詳細に施策の記録（行番号つき）。
  自動更新の変更判定に含めるため、保存すれば次の自動更新で全員の画面に反映。雛形は `tools/make_action_sheet.py`（openpyxl。設問を追加したら `--add-missing`）。
- **⑤AI Overview**：GSC「生成AI機能」レポートの日別表示回数（サイト別）と上位ページ。
- **ホーム**：「1) 今回の結論」の末尾に Google参考値の1行（AI向けに直す n 問／あと一歩／順位を上げる／検索チェック待ち）。

- **検索チェック【フェーズ2 実装済み】**：monitoring の GUI＋ブックマークレットで毎月記録した `google_check_dir`（既定：results_dir の隣の `google_check`）の
  `google_check_YYYY-MM.csv` を読む。フィルタ「判定に使う Google の値」＝自動（既定：検索チェックの観測キーワード → 未記録なら GSC）／検索チェック：キーワード／
  検索チェック：設問文／GSC。検索チェックで上位10件に自社なし（圏外）→「順位を上げる」。対象月は、Google 期間が月次ならその月、それ以外は記録のある最新の月。

  設問詳細に月別の記録（上位10件）、⑤に「検索チェック：AI による概要（Google が引用しているサイト）」。

### 回答分析｜回答本文のコンテキスト分析【実装済み】
回答全文（＝`results_*.csv` の `answer`／`logs/log_*.jsonl` と同一）を、社名だけでなく「どう答えているか」で分析。すべてオフラインのヒューリスティック（要目視）。
- **① 回答タイプ自動分類**：`classify_answer()` が各回答を `list`（社名列挙型・企業名候補2社以上）／`general`（一般論型）／`refusal`（留保・拒否型・`REFUSAL_HINTS` 該当）／`empty`／`error` に分類。ドメイン×ティアで構成を確認。
- **② 評価軸キーワード分析**：`detect_criteria()` が回答本文中の評価軸（`CRITERIA` 辞書：品質・実績・価格・納期・デザイン・ブランド・対応・別注・機能・サステナ・規模・業種特化）を検出。未言及の有効回答での頻度＝当社が勝つべき土俵＝強化すべきコンテンツの切り口。
- **③ 競合の文脈スニペット**：競合名を含む一文を回答本文から JS 側で抽出（本文は既に payload にあるため追加データ不要）。
- **④ 自社ヒット時の文脈**：当社が言及された回答の前後文＋共起する評価軸を表示。
辞書・閾値は `generate.py` の `CRITERIA`／`ATYPE_LABELS`／`REFUSAL_HINTS`／`classify_answer()` に集約。

### P2｜引用元URL分析【実装済み・データ待ち】
ヒット回答の `urls_found` を集計し、効いているページを特定。
非グラウンディングの現状は 0 件のため空状態を表示。キー許可後に自動有効化。

### P2｜自社サイト突合【実装済み】
`reference.md` の掲載実績（顧客・事例名）を AI 回答本文と突合。
**「掲載はあるが AI 未言及」＝ GEO 強化余地** をドメイン単位で可視化。

### P3｜競合サイト突合【将来】
AI 回答に実際に登場した競合サイトのみを取得し、被引用ギャップを比較。
ネット接続・取得制限への配慮が必要なため、オフライン自己完結の本体とは別工程で追加。

## 6. 競合抽出ロジック（透明性のための明文化）

回答本文の **太字表記（`**社名**`）** を主対象に、以下のヒューリスティックで候補を抽出する。

**採用条件（いずれか）**
- 企業サフィックス（株式会社・有限会社・ホールディングス・工業・製作所・商会・商事・産業）を含む
- 空白を含まない単一トークンの固有名詞（漢字/カナ/英字）で 2〜24 文字

**除外条件**
- 句読点・記号（。、！？：「」＝… 等）を含む説明句
- 一般語の断片（実績・ポイント・機能・体制・選定・対応・デザイン 等）
- 当社・自社ブランド（オンワード／オンワードコーポレートデザイン／オンワード樫山／Raffiria／ラフィーリア）
- `reference.md` から抽出した既知の掲載顧客名（＝競合ではなくエンドクライアント）＋ ハードコードの顧客ヒント

**位置づけ**：あくまで **候補（要目視確認）**。最終判断は各行ドリルダウンの回答全文で行う前提。
判定ロジックは `generate.py` の `extract_competitors()` / `_is_company_like()` / `_norm_key()` に集約。

## 7. アーキテクチャ

- **生成方式**：`generate.py`（Python 標準ライブラリのみ）が CSV と reference を読み、集計・抽出した結果を
  **JSON として単一 HTML に埋め込み** 出力する。
- **出力**：`analysis.html`（自己完結。外部依存は CDN の Chart.js のみ）。ブラウザ単体で開ける。
- **役割分担（処理）**：重い抽出（競合名の NLP 的抽出）は Python が行単位で 1 回だけ実施し、
  各行に候補配列を付与。フィルタ／集計／クロス表／ドリルダウンは HTML 内 JavaScript が動的に行う。
- **疎結合**：monitoring とは同じ CSV を読むだけ。monitoring 側の改修と独立に運用・改修できる。
- **セキュリティ**：埋め込み JSON は `<`, `>`, U+2028/2029 をエスケープし、回答本文の文字列が
  `</script>` 等でタグ境界を壊さないよう防御。

### ファイル構成
```
GEO-analysis/
├─ generate.py     … データ処理＋HTML生成（stdlibのみ）
├─ gsc_reader.py   … GSC の xlsx 読み込み（Google参考値タブ用・stdlibのみ）
├─ config.json     … データパス設定
├─ analysis.html   … 生成物（.gitignore 対象・再生成可能）
├─ README.md
├─ .gitignore
└─ docs/
   ├─ 分析アプリ_仕様書_v1.md   … 本書
   ├─ 引き継ぎプロンプト_v1.md
   └─ 実行手順書_v1.md
```

## 9. 制約・既知の注意

- 競合抽出はヒューリスティックで、候補にノイズ（非企業）や取りこぼしがあり得る。目視確認前提。

- `urls_found` は非グラウンディングでは空。P2 URL 分析はキー許可後に本格稼働。
